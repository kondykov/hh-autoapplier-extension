# Backend (server/)

ASP.NET Core 10 + PostgreSQL. Собирает вакансии, фильтрует/оценивает их, выбирает резюме и отдаёт клиенту готовую очередь.

Архитектура — DDD и простой CQRS без MediatR, решение и примеры: [adr/0001-backend-ddd-cqrs.md](adr/0001-backend-ddd-cqrs.md). Документация API: `http://127.0.0.1:8080/scalar` (без входа).

```
server/
  src/HhAutoApplier.Domain          агрегаты Vacancy, JobApplication, SearchProfile, ResumeProfile; value objects Salary, FilterRules;
                                    доменные сервисы VacancyEvaluator, ResumePicker, StackExtractor (без зависимостей)
  src/HhAutoApplier.Application     Commands/ и Queries/ по фичам (команда + обработчик), Dtos/, Extractors/,
                                    Errors/, порты Abstractions/ (IAppDbContext, IVacancySource)
  src/HhAutoApplier.Infrastructure  EF Core (Npgsql, Configurations/, миграции, DbSeeder); Sources/Hh — источник hh.ru;
                                    Collecting/ — фоновый сбор по расписанию; Telegram/ — бот (опрос и отправка уведомлений)
  src/HhAutoApplier.Api             контроллеры, Auth/ (cookie и X-Api-Key), OpenAPI + Scalar
                                    (Identity — в Infrastructure/Identity, роли — Domain/Users)
  tests/HhAutoApplier.Tests         xunit: домен, правила, разбор страниц hh.ru; Api/ — интеграционные тесты
                                    API (WebApplicationFactory + Postgres 17 в Testcontainers, нужен Docker)
  docker-compose.yml, Dockerfile    postgres:17 + api
```

## Запуск

```powershell
cd server
copy .env.example .env        # задайте POSTGRES_PASSWORD, ADMIN_EMAIL, ADMIN_PASSWORD (и при нужде LLM_API_KEY, TELEGRAM_BOT_TOKEN); токен расширения — POST /api/tokens
docker compose up -d --build  # api: http://127.0.0.1:8080, postgres: 127.0.0.1:${DB_PORT:-5433}
```

Миграции применяются при старте. Резюме «.NET» и «PHP» создаются при первом запуске, правятся через `PUT /api/resumes`.
Локально без Docker: поднимите Postgres и `dotnet run --project src/HhAutoApplier.Api`; тесты: `dotnet test`.

## Источники вакансий

Сборщик работает автономно внутри backend: фоновая задача раз в `Collector:IntervalMinutes` (и сразу при старте) проходит все включённые поиски всех пользователей по всем источникам. Найденная вакансия даёт отклик владельцу поиска — с правилами этого поиска и его резюме; уже известная вакансия заново не загружается. Одновременно идёт один проход. Вручную (только `Admin`): `POST /api/collect/start` запускает сбор в фоне, он не зависит от запроса и страницы; `GET /api/collect/status` отдаёт идущий проход и итог последнего (хранится в памяти до перезапуска сервера). `POST /api/collect` выполняет сбор внутри запроса и ждёт итога, обрыв запроса его прерывает.

**Источник — плагин** `IVacancySource` (порт в Application, реализации в `Infrastructure/Sources/`): `SearchAsync` возвращает карточки с выдачи (дёшево), `LoadDetailsAsync` дополняет новую вакансию описанием и навыками. Новый агрегатор — своя реализация и регистрация в `Infrastructure/DependencyInjection`. Сам сбор — `CollectVacanciesCommandHandler`.

**hh.ru** (`HhWebSource`, `Hh:Enabled`): публичные страницы поиска и вакансий без токена и аккаунта. Данные берутся из JSON `HH-Lux-InitialState`; разбор — только в `HhPageParser`, при смене вёрстки hh.ru правится он и тесты `HhSourceTests`. Поля поиска (`query`, `area`, `extraParams`) — параметры страницы `hh.ru/search/vacancy`.

Бережность: случайная пауза `Collector:DelayMinMs`–`DelayMaxMs` (2–5 с) между запросами, выдача листается до конца, но не больше `Collector:MaxPages` страниц (`COLLECT_MAX_PAGES`, по умолчанию 20), детали только для новых вакансий и подтверждаемых импортных карточек. Страница без новых не останавливает сбор: hh.ru показывает часть новых вакансий с задержкой, и они оказываются ниже уже известных. При нуле результатов hh.ru заполняет выдачу посторонними вакансиями, такая выдача считается пустой. Капча, 403 или 429 — `SourceBlockedException`: сбор останавливается до следующего запуска, в лог — предупреждение, `POST /api/collect` отвечает 502. Это серая зона условий hh.ru: аккаунт не используется, но частые запросы с одного IP могут включить антибот.

Запасной путь — **импорт** `POST /api/import` (`{search, vacancies[]}`): вакансии от любого клиента, например расширения. Карточка вакансии общая для всех пользователей, поэтому данным клиента не доверяем: ссылка — только `https` на `hh.ru` (иначе `https://hh.ru/vacancy/{id}`), карточка помечается `Imported`, и сбор заменяет её данными источника целиком — карточку, зарплату и описание. С выдачи приходит обрывок описания без зарплаты, поэтому любой отклик на ещё не подтверждённую импортную карточку, и самого импортёра тоже (#55; импорт — `waiting` в ответе — или сбор), не оценивается и ждёт в `New`: сбор загружает страницу вакансии и только тогда оценивает его правилами своего поиска и отправляет дальше. Значит, импортированное оценивается со следующим сбором, а не сразу, и пока источник заблокирован, ждёт.

Подтверждение бережное (#59): за проход — не больше `Collector:MaxConfirmations` карточек (по умолчанию 20, общий лимит на встреченные в выдаче и ждущие отклики), самые старые отклики первыми, остальные ждут следующих проходов. Страница не открылась (404 или нет данных) — отклики в `New` уходят в `Skipped` с причиной «вакансия недоступна» и больше не проверяются, карточка остаётся импортной. Блокировка источника (`SourceBlockedException`) недоступностью не считается: проход останавливается, отклики ждут. Отклики не в `New` подтверждение не меняет: если выдача встретит их карточку, обновится только она, статус и оценка останутся. Конфликт сохранения (отклик изменили, пока шёл запрос) проход не роняет: уже записанное остаётся, остальное — в следующем проходе.

Анкету расширение присылает только для отклика в очереди (`Queued`) — иначе 409: ответы LLM ведут сразу в очередь, и анкета не должна поднять туда отклонённое или ждущее проверки. Веб-интерфейс ставит в ссылки только `http(s)`.

## Вакансия и отклик (#8)

- `Vacancy` (`Domain/Vacancies`) — общая карточка: название, компания, зарплата, описание, стек, даты. Статуса и владельца в ней нет; с #9 поиск, нашедший вакансию, хранится в отклике (`SearchId`)
- `JobApplication` (`Domain/Applications`) — отклик пользователя на вакансию: статус, балл, причина статуса, резюме, вердикт, балл, причина и модель LLM, письмо, анкета с ответами, дата отклика. Все правила статусов — в его методах (`Evaluate`, `ApplyLlmEvaluation`, `Approve`/`Decline`, `SetCoverLetter`, `RequireAnswers`/`AnswerQuestions`, `MarkApplied`/`RecoverApplied`/`Skip`/`Fail`/`Reject`/`Invite`/`Requeue`, `Reevaluate`, `Hide`/`Unhide`), время передаётся аргументом. `MarkApplied` — только из `Queued` и `Questionnaire` (#60); `RecoverApplied` — отклик с потерянным статусом, найденный по чату hh.ru, из любого статуса до отправки. Имя не `Application` — чтобы не путать со слоем `HhAutoApplier.Application` (решение владельца 2026-10-25)
- История: каждая смена статуса добавляет в `History` событие `{at, from, to, reason}`
- Отсеянный отклик (#71): `Dismissed` — статус `Skipped`, то есть отклонённый или пропущенный вручную и отсеянный LLM или правилами; `Failed` сюда не входит, там есть «В очередь», а отклик «не подтверждён» мог уйти на hh.ru. `Reevaluate` возвращает на оценку с записью «повторная оценка» в истории: письмо LLM, ответы анкеты и прежний вердикт LLM сбрасываются, письмо, поправленное человеком (`manual`), остаётся. Карточка `Imported` ждёт в `New`, её подтвердит и оценит сбор; остальные сразу проходят правила и уходят в `Pending` или снова в `Skipped`. Без настроенной LLM сценарий отвечает 503 и ничего не меняет, в том числе для `Imported`. Суточный фильтр неудач письма (#80) не сбрасывается: после двух отказов за сутки письмо не напишется заново, и расширение возьмёт шаблон
- Скрытие (#71): `HiddenAt` — только показ в `GET /api/vacancies`; статус, история и `/api/stats` не меняются. Отклик не удаляется, поэтому сбор и импорт не создают его заново. Скрыть можно только `Dismissed`. Любая смена статуса, в том числе «В очередь» и «Оценить заново», снимает скрытие, чтобы отклик в работе не остался скрытым
- Таблица `JobApplications`: `VacancyId` → `Vacancies` и `UserId` → `AspNetUsers` (оба с каскадным удалением), анкета (`Questions`) и история (`History`) — колонки jsonb. Один отклик на пару (вакансия, пользователь), уникальный индекс `NULLS NOT DISTINCT`
- `UserId = null` — владелец по умолчанию (пока нет пользователей); с #9 отклики у каждого пользователя свои — см. «Владельцы данных»
- Миграция `JobApplications` перенесла данные: по отклику на вакансию, в истории — одно событие «перенос из вакансии (#8)»; `Down` копирует обратно. Статусы по-прежнему называются `VacancyStatus`
- API не изменился: ответы вакансий и очереди — карточка и отклик одним плоским объектом, плюс поле `history`

## LLM

Порт `ILlmClient` (Application) и `OpenAiCompatibleClient` (Infrastructure/Llm) — chat/completions любого OpenAI-совместимого провайдера; по умолчанию Groq. Настройки `Llm:*` (в `.env`: `LLM_API_KEY`, `LLM_BASE_URL`, `LLM_MODEL`, `LLM_DAILY_LIMIT`, `LLM_USER_DAILY_LIMIT`); без ключа LLM выключена. Доля пользователя (#56, решение владельца 2026-11-06: 150 из 300 в сутки UTC, 0 — без доли): `LlmUserQuota` считает ответы LLM в журнале `LlmCalls` по `UserId` (записи без модели — сбой провайдера — не считаются); исчерпавший долю не попадает в выборки проходов (иначе его отклики заняли бы всю пачку), его отклики ждут следующих суток, ему — одно сообщение в Telegram в сутки (`llm-quota:<дата>`). Не хватило на повтор анкеты — ответы первой попытки идут в `Review`. Повторы при 429 и 5xx (пауза — `Retry-After` или 1, 2, 4 с), таймаут, дневной лимит запросов (`LlmBudget`: счёт за сутки UTC, после перезапуска продолжается по журналу). Ключ Groq: https://console.groq.com/keys.

**Провайдеры** (#69). `Llm:Provider` (`LLM_PROVIDER`) выбирает запись реестра `LlmProviders` — профиль `LlmProviderProfile`: способ входа, поддержка `json_object`, минимальная `temperature`, нужен ли свой адрес. Клиент смотрит на профиль, а не на имя провайдера: новый провайдер — запись в реестре. Провайдер с обычным OpenAI-совместимым API и постоянным ключом подключается без правок кода: `LLM_PROVIDER=openai`, `LLM_BASE_URL`, `LLM_MODEL`, `LLM_API_KEY`; если модель не поддерживает `response_format`, ещё `LLM_JSON_MODE=none`. Если провайдер входит по короткоживущему токену, регистрируется `ILlmTokenSource`: клиент берёт токен на каждый запрос и при 401 один раз получает новый. `Llm:JsonMode` (`LLM_JSON_MODE`) задаёт JSON-режим явно: `json_object` или `none`, пусто — как в профиле, поддержка зависит и от модели. Неизвестный провайдер или режим, а также адрес Groq при провайдере со своим адресом останавливают старт API.

**Проверка ответов модели** (#67, для любого провайдера; выявлено на живом ГигаЧате — заглушки «[Ваше Имя]», выдуманный стаж словами, неполная анкета):

- Письмо: заглушки — в квадратных скобках и круглые на всю строку «(без подписи)», кроме дословных из шаблона — и сроки (числом или словами: «более трёх лет») сверяются с резюме, профилем и шаблоном, срок из требований вакансии стаж не подтверждает; так же сверяются цифры, обещания и технологии (#82, ниже в «Письма под вакансию»). Один повтор с замечаниями, затем отклик — на ручную проверку без письма: черновик остаётся в `LlmCalls`, «Одобрить» отправит отклик с шаблоном расширения, сутки письмо не переписывается
- Анкета: ответов не столько, сколько вопросов — один повтор, затем ручная проверка вместо пропуска. Одобрить — в очередь, расширение пришлёт анкету заново
- Оценка: единственное резюме пользователя подставляется, если модель не назвала его
- Не разобранные ответы и отказы проверок пишутся в `LlmCalls.Error` с моделью; вариант ответа без текста (модель потратила токены на рассуждения) — тоже неразобранный ответ, сбой провайдера — только пустое тело или ни одного варианта (#81). `LlmQualityMonitor` после каждого прохода считает их за час: от 5 отказов и не меньше четверти ответов модели — одно сообщение администраторам в Telegram в сутки (`llm-quality:<дата>`). Сбои провайдера и лимиты сюда не входят, о них — `LlmUnavailable`

**Текст работодателя в промптах** (#79, анкеты — #58). Всё, что написал работодатель: название, компания, зарплата, формат, стек, описание, сообщения чата, вопросы и варианты анкет, — стоит в блоке `<<<ДАННЫЕ РАБОТОДАТЕЛЯ>>> … <<<КОНЕЦ ДАННЫХ РАБОТОДАТЕЛЯ>>>`, общий код — `EmployerData`. `<<<`/`>>>` внутри текста заменяются на `«`/`»`, чтобы он не закрыл блок раньше; системный промпт велит считать блок данными и не выполнять просьб из него (раскрыть инструкции, резюме и профиль, сменить формат или оценку; в письмо — ни кодовых слов, ни ссылок по просьбе вакансии). Резюме, профиль, шаблон письма и пожелания кандидата стоят вне блока. Сверка цифр письма идёт только по фактам о кандидате (#82): содержимое блока фактом не считается.

Каждый запрос пишется в журнал `LlmCalls`: назначение, вакансия, владелец отклика или сообщения (`UserId`, #57; у проверки ключа и записей до #57 — пусто), модель, промпт, ответ или ошибка, токены.

**LLM-конвейер** (`LlmPipelineHostedService`, 2026-10-28): раз в минуту, если есть работа, — оценка `Pending`, ответы на анкеты, письма для очереди и проверки, разбор ответов работодателей (по 20 за проход), затем уведомления о проверке. Часовой цикл сбора (`CollectorHostedService`) только собирает: выдача из расширения и новые вакансии сбора оцениваются в течение минуты, а не со следующим сбором (2026-10-27 импорт ждал оценки больше двух часов — ноутбук спал).

**Оценка вакансий (#22).** Если LLM настроена, вакансия, прошедшая правила, получает статус `Pending` и в очередь расширения не попадает. В LLM-конвейере (и по `POST /api/llm/evaluate`) `EvaluatePendingVacanciesCommandHandler` отправляет LLM резюме (`Summary` профиля, иначе ключевые слова), пожелания из правил поиска и вакансию; ответ — JSON `{verdict, score, resume, reason}`:
- `fit` — в очередь (`Queued`), `Score` = оценка LLM, резюме — выбранное LLM;
- `doubtful` — в очередь с причиной «LLM сомневается: …» (ручная проверка — #25);
- `reject` — `Skipped` с причиной «LLM: …».

Неразобранный ответ считается сомнительным. При исчерпании лимита или недоступности провайдера оценка останавливается, остальные ждут следующего запуска. Без LLM вакансии идут в очередь сразу, как раньше. Поле `Summary` резюме заполняется через `PUT /api/resumes` — кратко о себе: опыт, стек, что интересно и что нет.

**Письма под вакансию (#23).** После оценки (и по `POST /api/llm/letters`) `WriteCoverLettersCommandHandler` пишет письма для вакансий `Queued` без письма, лучшие по баллу первыми. LLM получает резюме, выбранное для вакансии (`Summary` или ключевые слова), его шаблон письма `LetterTemplate` и вакансию. С шаблоном LLM сохраняет приветствие, стиль, подпись и контакты и меняет середину под вакансию; без шаблона пишет сама. Ответ — текст письма; пустой, слишком короткий или JSON не сохраняется, вакансия ждёт следующего запуска, а после двух таких ответов сутки не запрашивается (#80; считаются `LlmCall.Unparsed` вместе с отказами проверок, сбой провайдера — нет: ответа не было, письма напишутся после восстановления). Промпт строгий: имя, подпись и контакты — только из шаблона (без шаблона — письмо без них), цифры, стаж, навыки и места работы — только из резюме и шаблона, ключевые слова без `Summary` не выдаются за опыт (живая проверка 2026-10-25: без `Summary` LLM выдумывала имя и стаж). Запреты промпта модель обходит (живой прогон #82), поэтому письмо проверяет сервер, только по фактам о кандидате — резюме, профиль, шаблон (`CoverLetterWriting.Facts`); текст вакансии фактом не считается. Цифры: каждое число или диапазон должны быть в фактах, а «до», «более», «свыше», «почти» при числе — в том же сочетании («более N» — можно при «N+»); не считаются цифрами названные в письме компания и должность целиком, токены вроде «1С» и «2ГИС» из них, технология с версией в контексте намерения, а версия при опыте — считается («ASP.NET Core (6+)»). Обещания (`CoverLetterClaims.Promises`): готовность к тестовому заданию, зарплата (желаемая, ожидаемая, её обсуждение), решение примера — законны, только если это есть в фактах или шаблоне. Технологии (`CoverLetterClaims.Technologies`, словарь `StackExtractor` с его границами и синонимами): упомянутая и отсутствующая в фактах — отказ, кроме намерения («готов освоить», «изучить», «интересно», «хочу»), честного «не работал» и названия компании или роли; язык следует из фреймворка (C# и .NET, Laravel — PHP, React — JavaScript). Любой отказ — одна повторная попытка с перечнем замечаний, а если и она не прошла — отклик на ручную проверку без письма, сутки не переписывается (журнал `LlmCalls` по вакансии и владельцу, #57 — неудачи одного пользователя не лишают писем другого; ошибки «цифры не из фактов», «заглушки в письме», «обещания не из фактов», «технологии не из фактов»; живые письма 2026-10-28: «на 30–40%» превращалось в «до 30 %»). Письмо (`coverLetter`) уходит в расширение вместе с `/api/queue` и в режиме «из очереди» важнее шаблонов расширения. Без LLM писем нет. Переписать письма очереди после правки резюме, шаблона или промпта: `POST /api/llm/letters/reset` (все или `{vacancyIds}`; письма администратора, `?userId=` — другого пользователя; поправленные человеком — только с `includeManual: true`, #57), затем `POST /api/llm/letters` или фоновый запуск.

**Профиль кандидата (#35).** Один на пользователя, общий для всех резюме (`CandidateProfiles`, навыки — jsonb): общая часть (уровень, стаж, формат, город, языки, пожелания) и факты по навыкам — навык (синонимы через «/», например «EF Core / Entity Framework») → где применял, сколько, что делал, цифры. Под вакансию `CandidateContext` кладёт в промпт общую часть и факты только по навыкам этой вакансии: стек навыка по словарю `StackExtractor` пересекается со стеком вакансии или название навыка упомянуто в тексте целым словом. Так во всех четырёх промптах — оценка, письмо, анкета (ещё и по тексту вопросов), разбор ответа работодателя (по названию и тексту сообщения); `Summary` резюме остаётся описанием направления. Пустой профиль — промпты как раньше. API — `GET/PUT /api/profile`, в веб-интерфейсе — «Резюме» → «Профиль кандидата».

**Ручная проверка (#25).** LLM сомневается (`doubtful`) — вакансия получает статус `Review` и в очередь расширения не идёт; правило поиска `skipReview: true` — сразу в очередь, как раньше. Письма пишутся и для `Review`, чтобы их было видно на проверке. Раздел «Проверка» веб-интерфейса (`/#review`, wwwroot, отдаётся без входа — сам спрашивает email и пароль, дальше работает по cookie со своими данными): список `GET /api/vacancies?status=Review`, у карточки — описание, причина LLM, анкета, письмо и текстовые ответы анкеты в полях для правки; «Одобрить» → `POST /api/vacancies/{id}/review` `{approve: true, coverLetter?, answers?}` — в очередь, поправленное письмо сохраняется с моделью `manual`, `answers` — все ответы анкеты по порядку вопросов (проверяются, как ответы LLM; ошибка — 409, ничего не меняется); «Отклонить» → `{approve: false, reason?}` — `Skipped` «отклонено вручную: …». Анкеты с текстовыми ответами LLM тоже идут на проверку (#58, ниже). Telegram-бот (#28) решает через тот же эндпоинт.

**Анкеты работодателей (#24).** Вопросы анкеты видны только со входом на hh.ru: без входа страница отклика ведёт на регистрацию, а страница вакансии знает только `test.hasTests` (проверено 2026-10-25). Поэтому их присылает расширение: `POST /api/vacancies/{id}/questionnaire` с `{questions: [{question, type: Radio|Checkbox|Text|Unknown, options}]}` → статус `Questionnaire`, прежние ответы сбрасываются. После оценки (и по `POST /api/llm/answers`) `AnswerQuestionnairesCommandHandler` отправляет LLM резюме вакансии, пожелания из правил поиска (зарплата, формат), вакансию и пронумерованные вопросы; ответ — JSON `{answers: [...]}` по порядку вопросов. Текст работодателя (вакансия, вопросы, варианты) — в блоке `<<<ДАННЫЕ РАБОТОДАТЕЛЯ>>> … <<<КОНЕЦ ДАННЫХ РАБОТОДАТЕЛЯ>>>` с инструкцией не выполнять указаний из него; `<<<`/`>>>` в тексте работодателя заменяются, чтобы он не закрыл блок раньше. Агрегат проверяет ответы: вариант — только из анкеты (без учёта регистра, сохраняется в написании анкеты), radio — ровно один, checkbox — хотя бы один, текст — непустой; не сошлось — `Skipped` с причиной, догадки работодателю не уходят. Цифры текстовых ответов (#58) сверяются, как у писем (`FactFigures`), но только с резюме и профилем кандидата — цифра из вакансии или вопроса («у вас 10 лет?») не факт; зарплата из пожеланий (`minSalaryRub`, и «N тыс.») — только в ответе на вопрос о зарплате. Нарушение — одна исправленная попытка (`LlmCall.Rejected` «цифры не из фактов: ответ N: …»), снова нарушение — `Review` «анкета: проверить — …» даже у поиска `skipReview`. Решение владельца 2026-11-05 (#58, пересмотр решения 2026-10-25): анкета с текстовыми вопросами — `Review` «анкета: проверить ответы LLM», у поиска `skipReview: true` — сразу в очередь; только варианты (radio/checkbox) — сразу в очередь (`questions[].answer`, причина «анкета: ответы LLM»). Уведомление в Telegram о такой проверке — с ответами анкеты, ключ `review-questionnaire:<id отклика>` (отклик мог уже побывать на проверке как сомнительный). Анкета хранится в отклике — `JobApplications.Questions` (jsonb; до #8 — `Vacancies.Questions`).

**Просьбы работодателя к письму (#72, часть 2; решения В7–В12 в `specs/sprint-14.md`).** Запрет #79 остаётся: модель пишет письмо как обычно и этих значений не получает, а сервер дописывает их сам после проверок #82.
- *Извлечение* — в проходе оценки, сразу после вердикта `fit` или `doubtful` и до смены статуса, иначе расширение забрало бы отклик раньше. Описание вакансии хранится до 20 000 знаков (промпты письма и оценки по-прежнему берут первые 3000). Широкий фильтр `LetterRequestExtraction.MayContainRequests` без LLM: нет совпадения — просьб нет, запроса нет. Совпадение — запрос `letter-requests` с текстом в блоке `EmployerData`, ответ только типизированный JSON `{requests: [{type, quote, value}]}`. Журнал `LlmCalls`, учёт в `LlmQualityMonitor`.
- *Состояние* `JobApplications.LetterRequestsState`: `NotExtracted` (старый отклик или ещё не оценён), `None`, `Found` (есть незакрытые), `Closed`, `Failed`. Просьбы — jsonb `LetterRequests`. Пустой или неразобранный ответ — «неизвестно», а не «просьб нет»: не больше двух запросов на отклик за сутки (`MaxRequestsPerDay`), затем `Failed` и `Review`. Сбой провайдера или кончившаяся доля — отклик остаётся `Pending`.
- *Значения.* Пример считает `ArithmeticCalculator` (только числа и `+ - * / ( )`, до 64 знаков; мусор, деление на ноль и `1/3` — `Review`). Выражение и кодовое слово должны дословно быть в описании; в письмо идёт запись, собранная из токенов, а не текст работодателя. Зарплата и готовность — только `CandidateProfile.DesiredSalaryRub` и `ReadyForTestTask`; значение модели для них не читается, `MinSalaryRub` не используется. Кодовое слово — одно слово из букв и цифр до 30 знаков, вставляется только после подтверждения человеком. Прочее (ссылки, контакты, внешние действия) не выполняется: только показывается.
- *Письмо.* После проверок `CloseLetterRequests` дописывает блок «Ответы на вопросы из вакансии» (`LetterAnswers`): перед последним абзацем шаблона, если письмо им заканчивается, иначе в конец. Проверки #82 блока не видят. Длиннее лимита поля письма — просьбы остаются открытыми.
- *Куда идёт отклик.* Как текстовые анкеты #58: на проверку, кроме поиска `skipReview`; незакрываемая просьба и `Failed` — на проверку всегда. `/api/queue` выдаёт только `NotExtracted`, `None` и `Closed` с письмом: при письме `null` расширение взяло бы шаблон. «В очередь» с открытыми просьбами возвращает на проверку. «Одобрить» закрывает оставшиеся просьбы решением человека, но без письма отвечает 409; в Telegram одобрить с открытыми просьбами нельзя, просьбы видны в сообщении.
- *Проверка:* `POST /api/vacancies/{id}/letter-requests/resolve {confirmCodeWords?: [номер]}` — подтвердить кодовые слова и подставить значения из профиля, блок в письме заменяется, статус не меняется.

**Исходящий VPN (#5).** С российского IP Groq отвечает 403, Telegram API не отвечает, а hh.ru должен идти напрямую. `docker-compose.vpn.yml` добавляет контейнер xray: через VPN идут только домены из правил `xray/base.json` (`api.groq.com`, `api.telegram.org`), всё остальное — напрямую. API ходит через него по `HTTPS_PROXY`; hh.ru и внутренние имена — в `NO_PROXY`, поэтому сбор вакансий не зависит от xray. VPN недоступен — запросы к этим доменам падают, а напрямую не уходят (проверено заглушками). Включение описано в начале `docker-compose.vpn.yml`; параметры сервера — `xray/outbound.json`, только на сервере, не в git. Новый LLM-провайдер за VPN — ещё одна строка в правиле `base.json`.

## Пользователи и вход (#7)

ASP.NET Core Identity (таблицы `AspNet*` в той же БД, миграция `Identity`). Роли `Admin` и `User` (`Domain/Users/Roles.cs`).
- Пользователей создаёт только администратор, саморегистрации нет (решение владельца 2026-10-25)
- Первый администратор создаётся при старте из `Admin:Email`/`Admin:Password` (`.env`: `ADMIN_EMAIL`, `ADMIN_PASSWORD`), только пока администраторов нет. **Пароль в `.env` — открытым текстом:** после первого старта сменить его (`POST /api/auth/password`) и очистить `ADMIN_PASSWORD` — дальше он не нужен (пустой пароль сидер пропускает); `ADMIN_EMAIL` оставить (общий ключ и перенос данных без владельца). Для развёртывания (#5) — заменить способ создания первого администратора, см. `ROADMAP.md`, «Технический долг»
- Вход по email и паролю → cookie `hh_auth` (HttpOnly, SameSite=Strict, 14 дней, продлевается при работе). Без входа — 401, без прав — 403 (без перенаправлений)
- Пароль: не короче 10 символов, 4 разных символа, без требований к классам. 5 неудачных попыток — вход закрыт на 15 минут
- Блокировка, смена роли или пароля обрывают сессии пользователя не позже чем через минуту (security stamp)
- Расширение входит персональным токеном в заголовке `X-Api-Key` — обработчик `Api/Auth/ApiKeyAuthenticationHandler`, см. «Персональные токены». Общий ключ `API_KEY` убран (#42, 2026-10-28). Cookie и токен проходят через один `[Authorize]`
- Без входа: `/health`, `/scalar`, `/openapi`, страницы wwwroot (`/`, `/review.html`, `/dialogs.html`), `POST /api/auth/login`

## Владельцы данных и доступ (#9)

- Поиски и резюме — у владельца (`UserId`; `null` — владелец по умолчанию, пока нет пользователей). Имена уникальны в пределах пользователя (`NULLS NOT DISTINCT`). `Vacancy` общая
- Отклик хранит `SearchId` — поиск владельца, нашедший вакансию (FK, при удалении поиска — `SET NULL`). Его правила идут в LLM-оценку и анкеты, из него — `searchName` в ответах API
- Все эндпоинты данных (поиски, резюме, вакансии, очередь, статистика, отчёт, статус, проверка, анкета, импорт) работают с данными текущего пользователя. Списки `/api/searches`, `/api/resumes`, `/api/vacancies`, `/api/stats`, `/api/report` принимают `?userId=`: `Admin` читает данные другого пользователя (только чтение), не-админ — 403. `/api/queue` — всегда свои (её читает расширение)
- Доступ: эндпоинты данных — любой вошедший (fallback-политика — вход обязателен), роль `User` получает только своё; `/api/users*`, `/api/collect`, `/api/llm/*` — только `Admin`
- Токен `X-Api-Key` действует от имени своего владельца, но всегда с ролью `User` (минимум прав: утёкший токен не управляет пользователями, не запускает сбор и LLM, не читает чужое, не меняет пароль; его можно отозвать). Владелец заблокирован или удалён — 401. `/api/auth/me` показывает `viaApiKey`
- При старте данные с `UserId = null` переходят первому активному администратору, кроме совпадающих с его собственными (то же имя поиска или резюме, та же вакансия)
- Сборщик и фоновые проходы LLM обрабатывают всех пользователей: резюме владельца, правила поиска отклика
- Миграция `DataOwners`: `UserId` у `Searches` и `Resumes`, `SearchId` у `JobApplications` (заполняется по `Vacancies.SearchName`), уникальность в пределах пользователя; проверена up/down/up на копии настоящих данных. `Down` падает (с откатом), если имена у разных пользователей совпадают
- Открыто на потом: каскадное удаление данных пользователя (FK `Cascade`) — решить про мягкое удаление
- Одновременная смена отклика (#54): `JobApplication` — с токеном конкурентности `xmin` (миграция `JobApplicationVersion` меняет только модель: колонка системная). LLM-конвейер сохраняет результат через `SaveOrDiscardAsync`: отклик изменили, пока LLM отвечала, — результат отбрасывается, вызов остаётся в `LlmCalls`. Ручной запрос, опоздавший к записи конвейера, — 409 (`ConcurrencyConflictMiddleware`). Проходы конвейера — по одному: фон и ручные `/api/llm/*` ждут `LlmPipelineGate` (один экземпляр api)

## Персональные токены (#10)

- `POST /api/tokens` `{name}` — выпустить токен `hh_…` (значение показывается один раз), `GET /api/tokens` — свои (только начало `prefix`), `DELETE /api/tokens/{id}` — отозвать. Выпуск — только после входа по паролю: токеном новый не выпустить.
- Токен передаётся в заголовке `X-Api-Key`, в панели расширения — поле «Токен». Действует от имени владельца с ролью `User`; отозван, владелец заблокирован или удалён — 401.
- В базе — только SHA-256 токена (`ApiTokens`, уникальный индекс по хэшу). Общий ключ `API_KEY`/`API_KEY_USER` убран (#42, 2026-10-28): значение без префикса `hh_` или не найденное в базе — 401. Ветка «пользователей нет — данные владельца по умолчанию по ключу» убрана вместе с ним: токен есть только у пользователя (самый безопасный вариант).

## Telegram (#28)

Бот на backend: уведомления и ручная проверка из чата. Включается токеном от @BotFather в `.env` (`TELEGRAM_BOT_TOKEN`, `Telegram:BotToken`); без токена бот выключен, уведомления не пишутся. Пакет `Telegram.Bot` (22.10, решение владельца 2026-10-26) — только в `Infrastructure/Telegram`, сценарии — в Application за `ITelegramBot`.

- **Привязка чата:** после входа по паролю `POST /api/telegram/link` → одноразовый код на 15 минут и ссылка `t.me/<бот>?start=<код>`; пользователь отправляет боту `/start <код>`. Ключом или токеном код не получить: чат получает право одобрять и отклонять отклики. У пользователя один чат, чат — у одного пользователя (привязка к другому снимает прежнюю). В базе — только SHA-256 кода (`TelegramChats`). Бот отвечает только в личном чате.
- **Команды:** `/status` — очередь, проверка, анкеты, отклики за сутки; `/review` — отклики `Review` (до 10) с кнопками «Одобрить» / «Отклонить» (правила те же, что в разделе «Проверка», письмо — как написала LLM; поправить письмо — на странице); `/help`; `/stop` — отвязать (с подтверждением кнопкой). **Кнопки (#45):** меню внизу чата («Статус», «На проверке», «Помощь» — присылают свою подпись, бот понимает её как команду; показывается после привязки и справки, убирается при отвязке), меню команд «/» (`SetMyCommands` при старте); под `/status` — «На проверке (N)», если есть что проверять; под сводкой — «Решить по одному»; под ответом работодателя — «Обработано» (как в разделе «Ответы работодателей»). Data кнопок — `действие:аргумент` (`approve`/`decline:<id вакансии>`, `review:`, `handled:<id чата>`, `unlink:`, `cancel:`); тексты и раскладка — `BotTexts`, разбор — `HandleTelegramCallbackCommandHandler`. Заблокированный пользователь — бот не выполняет команды и не шлёт уведомления.
- **Уведомления (outbox `Notifications`):** сценарий пишет уведомление, `TelegramHostedService` доставляет раз в 5 с (до 5 попыток; бот остановлен пользователем — отмена). Ключ `(UserId, Key)` уникален — одно событие, одно сообщение:
  - отклик на проверке — после писем LLM, с кнопками (`review:<id отклика>`); больше трёх новых за проход — одна сводка со списком и ссылкой на `/review` и раздел «Проверка» (`review-digest:<id>`, решение владельца 2026-10-28), уведомления откликов сводки сразу отменяются;
  - анкета без ответа LLM — отклик пропущен (`questionnaire:<id>`);
  - события расширения `POST /api/events` `{kind: Captcha|DailyLimit, message?}` — капча (раз в час) и дневной лимит (раз в сутки), владельцу ключа или токена;
  - приглашение или вопрос работодателя — с разбором LLM и черновиком ответа (#26);
  - администраторам — источник заблокировал сбор и LLM остановилась (лимит, провайдер), раз в сутки на вид.
- Приём — long polling (`getUpdates`), вебхук не нужен: сервер без адреса в интернете. Один токен — один работающий экземпляр (второй получает 409).

## Ответы работодателей (#26)

Расширение по кнопке «Автоответ» на странице чатов hh.ru забирает чаты откликов из API страницы «Чаты» (`chatik.hh.ru/chatik/api/chats`, только GET — сообщения не помечаются прочитанными; до 3 страниц по 20 чатов, не старше 30 дней) и отправляет их в `POST /api/dialogs`: по чату — последнее сообщение, его автор и состояние отклика hh.ru (`applicantState`).

- **Статусы:** `DISCARD` → отклик `Rejected` (из `Applied` или `Invited`), `INVITATION`/`INTERVIEW` → новый статус `Invited` (из `Applied`). Чат по вакансии бывает только после отклика: отклик с потерянным статусом (`Failed`, `Queued`…) сначала становится `Applied` (`recovered` в ответе).
- **`EmployerMessage`** (`Domain/Dialogs`, таблица `EmployerMessages`, миграция `EmployerMessages`): одна запись на чат пользователя — последнее сообщение работодателя, вид (`Rejection`, `Invitation`, `Question`, `Other`), пересказ, черновик ответа, «обработано», автоответ. Новое сообщение работодателя заменяет прежнее и сбрасывает разбор; последнее сообщение от пользователя — он ответил сам (обработано).
- **Разбор:** отказ — по состоянию hh.ru, без LLM (решение владельца 2026-10-26: экономит лимит). Остальное разбирает LLM (`DialogAnalysis`, журнал `LlmCalls` с назначением `dialog-analysis`) в LLM-конвейере `LlmPipelineHostedService` раз в минуту; неразобранный ответ модели — «прочее» без черновика. Приглашения и вопросы — в Telegram с пересказом, ссылкой на чат и черновиком (`dialog:<chatId>:<messageId>`). Черновик — без выдуманных фактов, с заглушками `[удобное время]`; отправляет человек.
- **Автоответ на отказ** (решение владельца 2026-10-26, меняет «чаты — человек» из #4 для отказов): короткое «спасибо» из панели расширения. Только на отказы, пришедшие после первого сбора пользователя. `POST /api/dialogs` возвращает чаты, где автоответ ждёт отправки; расширение проверяет `writePossibility` (`chat_data`, GET) и сообщает итог в `POST /api/dialogs/{chatId}/auto-reply`. После отказа hh.ru обычно закрывает переписку до приглашения (`WITHOUT_INVITATION`) или работодатель закрыл её сам (`DISABLED_BY_EMPLOYER`) — тогда автоответ `Unavailable` с причиной. Пробный режим расширения ничего не отправляет.
- Раздел «Ответы работодателей» веб-интерфейса (`/#dialogs`): необработанные приглашения и вопросы с черновиком — «Копировать и открыть чат», «Обработано».

Пример поиска: `PUT /api/searches` с `{"name":"dotnet","query":"C# .NET","area":"113","extraParams":"work_format=REMOTE","rules":{"excludeKeywords":["1С"],"levelKeywords":["junior"],"minSalaryRub":200000}}`.

**Стоп-слова и слова уровня (#72).** `excludeKeywords` ищутся в названии, описании и стеке и сразу дают `Skipped`. `levelKeywords` ищутся только в названии и отсеивают лишь при явном признаке — `workExperience` равен `noExperience` или стоит флаг `internship` (причина «слово уровня «junior»: без опыта»). Опыт 1–3 года или неизвестный опыт — вакансия идёт дальше, и решает LLM. Слова уровня не попадают в пожелания кандидата (`не интересно: …`), даже если остались и в стоп-словах; модель получает «Требуемый опыт» и указание считать расхождение названия с требованиями поводом для `doubtful`, а не для `reject`, и называть его в причине.

Требуемый опыт — `Vacancy.WorkExperience`, код со страницы вакансии (`vacancyView.vacancyFull.vacancy.workExperience`: `noExperience`, `between1And3`, `between3And6`, `moreThan6`). Флаг `internship` на той же странице важнее опыта и хранится в том же поле значением `internship`. У старых и неподтверждённых импортных карточек — `null`. В ответах API — необязательное поле `workExperience` текстом («1–3 года»), на карточке веб-интерфейса — «опыт: …». Без настроенной LLM вакансия со словом уровня и без явного признака идёт сразу в очередь, как любая прошедшая правила. Старые `Skipped` с причиной «стоп-слово» сами не меняются: их возвращает «Оценить заново».

## Ограничения (#60)

Расчёт на один экземпляр backend (локальное развёртывание): для него это не дефекты.

- **Outbox Telegram:** `MarkSent` сохраняется после отправки. Если сообщение ушло, а сохранение упало, оно уйдёт повторно.
- **Несколько экземпляров:** сбор вакансий, LLM-конвейер и доставка outbox работают без блокировок между процессами (`LlmPipelineGate` — только внутри процесса). Второй экземпляр на той же базе задвоит запросы к hh.ru и LLM и сообщения в Telegram; опрос бота с тем же токеном получит 409.
